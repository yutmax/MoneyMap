# MoneyMap — техническое задание

> Версия документа: 1.0 · 2026-10-05
> Статус: согласовано, к реализации

---

## 1. Назначение

MoneyMap — веб-приложение для личного финансового учёта с поддержкой нескольких счетов в разных валютах и криптовалютах.

Приложение решает четыре задачи:

1. **Учёт** — фиксация доходов, расходов и переводов между своими счетами.
2. **Мультивалютность** — счета в любых фиатных и криптовалютах, ввод операций в любой валюте с конвертацией в валюту счёта, сводный баланс по всем счетам в выбранной валюте.
3. **Автоматизация** — регулярные списания с фиксированной суммой и датой (подписки, коммунальные платежи, кредиты) создаются сами.
4. **Сверка** — приложение напоминает ввести фактический остаток в выбранную дату и показывает расхождение между фактом и расчётом.

### 1.1. Целевой сценарий использования

Пользователь работает с приложением с нескольких устройств (рабочий ноутбук, домашний компьютер, телефон). Повторный ввод логина и пароля после перезагрузки браузера не требуется. В профиле виден список активных сессий с возможностью отозвать любую из них.

### 1.2. Модель доступа

Данные каждого пользователя полностью изолированы. Общие (семейные) бюджеты в первой версии не поддерживаются, но слой доступа к данным проектируется так, чтобы их добавление не требовало переписывания запросов (см. §5.4).

## 2. Глоссарий

| Термин                                  | Значение                                                                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Счёт** (account)                      | Место хранения денег: наличные, банковская карта, вклад, криптокошелёк. Имеет одну валюту.                    |
| **Транзакция** (transaction)            | Одна операция: доход, расход или одна нога перевода.                                                          |
| **Перевод** (transfer)                  | Перемещение денег между двумя своими счетами. Представлен двумя транзакциями, связанными `transfer_group_id`. |
| **Валюта счёта**                        | Валюта, в которой ведётся учёт на этом счёте. Неизменяема после создания.                                     |
| **Базовая валюта**                      | Валюта пользователя, в которой показывается сводный баланс по всем счетам.                                    |
| **Регулярное правило** (recurring rule) | Шаблон повторяющейся операции с периодичностью и датой.                                                       |
| **Экземпляр** (occurrence)              | Конкретная транзакция, сгенерированная из регулярного правила на конкретную дату.                             |
| **Снапшот остатка** (balance snapshot)  | Зафиксированный пользователем фактический остаток на счёте на определённую дату.                              |
| **Сверка** (reconciliation)             | Сопоставление фактического остатка с расчётным и выявление расхождения.                                       |

## 4. Архитектура

### 4.1. Структура репозитория

```
moneymap/
├── apps/
│   ├── api/                    # Fastify + Drizzle + pg-boss
│   │   ├── src/
│   │   │   ├── db/             # схема Drizzle, миграции
│   │   │   ├── modules/        # по доменам: auth, accounts, transactions, ...
│   │   │   ├── jobs/           # воркеры pg-boss
│   │   │   ├── lib/            # money, fx, scoping, errors
│   │   │   └── server.ts
│   │   └── Dockerfile
│   └── web/                    # Vite + React, Feature-Sliced Design
│       ├── src/
│       │   ├── app/            # провайдеры, роутер, гарды, глобальные стили
│       │   ├── pages/          # экраны маршрутов, только композиция
│       │   ├── widgets/        # составные блоки: шапка, карточка авторизации
│       │   ├── features/       # действия пользователя: вход, онбординг, смена пароля
│       │   ├── entities/       # предметные сущности: user, session, currency
│       │   └── shared/         # ui-кит, http-клиент, утилиты, токены стилей
│       └── index.html
├── packages/
│   └── shared/                 # zod-схемы, типы, денежные утилиты
├── docs/
│   └── SPEC.md
├── compose.dev.yml             # только Postgres + pgweb
├── compose.prod.yml            # api + postgres + caddy
├── Caddyfile
└── pnpm-workspace.yaml
```

Фронтенд разложен по Feature-Sliced Design. Слой импортирует только то, что лежит строго ниже него — `app → pages → widgets → features → entities → shared` — и обращается к соседнему слайсу исключительно через его `index.ts`. Направление импортов проверяется линтером (`no-restricted-imports` в `eslint.config.js`), а не договорённостью: правило, которое ничто не проверяет, перестаёт выполняться на третьей неделе.

Что это даёт на практике: форма входа лежит в `features/auth-login` вместе со своим запросом, а страница `pages/login` только собирает её с карточкой из `widgets/auth-card`. Запрос «кто я» объявлен один раз в `entities/user` — его используют и гарды маршрутов, и шапка, и страница настроек, не зная друг о друге.

`packages/shared` — ключевой элемент раскладки: схема валидации объявляется один раз, бэкенд проверяет ею входящие запросы, фронтенд — поля формы, типы на обеих сторонах выводятся автоматически.

### 4.2. Разделение окружений

- **Разработка**: в Docker поднимается только Postgres и pgweb. API и фронтенд запускаются нативно (`pnpm dev`) — это сохраняет работоспособность Vite HMR и отладчика, которые на Windows деградируют при bind-монтировании кода в контейнер.
- **Продакшн**: контейнеризировано всё. Прод-`Dockerfile` пишется с первого дня, чтобы несовместимости выявлялись сразу, а не на деплое.

### 4.3. Топология продакшна

```
                    ┌─────────────────────┐
  :443 ───────────▶ │ Caddy               │  HTTPS (Let's Encrypt)
                    │  /api/*  → api:5000 │
                    │  /*      → web/dist │  статика
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐    ┌──────────────┐
                    │ api (Fastify)       │───▶│ postgres     │
                    │ + воркер pg-boss    │    │ volume       │
                    └─────────────────────┘    └──────────────┘
```

Фронтенд в продакшне — статические файлы, собранные Vite, отдаются Caddy напрямую. Отдельный Node-процесс для него не нужен.

HTTPS обязателен не только по соображениям безопасности: refresh-куки выставляются с флагом `Secure`, то есть без TLS механизм аутентификации нефункционален.

## 5. Ключевые технические принципы

Нарушение любого из этих пяти принципов приводит к расхождению балансов, которое крайне трудно диагностировать задним числом.

### 5.1. Деньги не хранятся в числах с плавающей точкой

- В БД: `NUMERIC(38, 18)` — покрывает 8 знаков Bitcoin и 18 знаков Ethereum.
- В JS: строки, арифметика через `decimal.js`.
- В API: строки (`"1234.56"`), не `number`.
- Целочисленные минорные единицы (`BIGINT`) не используются: на 18 знаках точности они переполняются.
- Правила отображения и округления берутся из поля `decimals` таблицы `currencies`, форматирование — `Intl.NumberFormat`.

### 5.2. Курс конвертации фиксируется в транзакции

Каждая транзакция хранит одновременно:

- `amount_original` + `currency_original` — то, что ввёл пользователь;
- `amount_account` + `fx_rate` — сумма в валюте счёта и применённый курс.

Курс записывается в саму транзакцию и впоследствии не пересчитывается. Если хранить только исходную сумму и конвертировать при чтении, исторические отчёты будут меняться при каждом изменении курса. Прошлое неизменяемо.

### 5.3. Генерация регулярных операций идемпотентна

На таблице `transactions` действует `UNIQUE (recurring_rule_id, occurrence_date)`. Повторный запуск воркера не создаёт дубль списания. То же для напоминаний — уникальность по периоду срабатывания.

### 5.4. Доступ к данным — через единый слой скоупинга

Все запросы проходят через хелпер, подставляющий владельца, а не через россыпь `where(eq(table.userId, ...))` по модулям. Это одновременно защита от утечки данных между пользователями и подготовка к возможному переходу на семейные бюджеты: замена `user_id` на `workspace_id` затронет одно место.

### 5.5. Финансовые записи не удаляются физически

Везде `deleted_at` (soft delete). История должна быть восстановима.

## 6. Аутентификация и сессии

### 6.1. Схема токенов

| Токен   | Тип                                                | Время жизни | Хранение                                  |
| ------- | -------------------------------------------------- | ----------- | ----------------------------------------- |
| Access  | JWT (HS256), payload `{ userId, sessionId }`       | 15 минут    | httpOnly cookie                           |
| Refresh | Случайная строка, 32 байта из `crypto.randomBytes` | 60 дней     | httpOnly cookie, `path=/api/auth/refresh` |

Refresh-токен — непрозрачный (opaque), не JWT: его нужно уметь отзывать, а JWT по своей природе отозвать нельзя.

### 6.2. Хранение

В таблице `sessions` лежит **только SHA-256 хеш** refresh-токена — по той же логике, что и пароль: утечка дампа БД не даёт возможности войти.

### 6.3. Ротация и детекция кражи

1. При каждом обращении к `/api/auth/refresh` выдаётся новый refresh-токен, предыдущий помечается использованным.
2. Если предъявлен уже использованный токен — это признак компрометации. Вся сессия отзывается немедленно, пользователю отправляется уведомление.
3. `last_used_at` обновляется при каждом refresh — по нему строится список активных устройств.

### 6.4. Управление сессиями

Пользователь видит список своих сессий: устройство (разобранный User-Agent), IP, дата создания, последняя активность, признак текущей сессии. Доступны операции: отозвать конкретную сессию, отозвать все кроме текущей.

### 6.5. Защита

- Куки: `httpOnly`, `secure`, `sameSite=lax`. Refresh-кука ограничена путём `/api/auth/refresh`.
- **CSRF**: обязательна, так как аутентификация на куках. Double-submit token + проверка кастомного заголовка.
- Rate limiting на `/login`, `/register`, `/refresh` — по IP и по email.
- Пароли: argon2id. Минимальная длина 8 символов, проверка по списку скомпрометированных (k-anonymity API Have I Been Pwned). Нижняя граница выбрана в паре с этой проверкой: на шести знаках практически любой пароль, который человек способен придумать, уже встречается в дампах, и форма обещала бы шесть, отклоняя почти всё введённое.
- Перечисление пользователей (user enumeration) исключено: одинаковый ответ и время отклика при неверном email и неверном пароле.

## 7. Модель данных

Все таблицы с пользовательскими данными имеют `user_id`, `created_at`, `updated_at`; финансовые — дополнительно `deleted_at`.

```sql

  base_currency      text        -- валюта сводного баланса; null до онбординга
```

### 7.1. Соглашение о знаке суммы

`amount_account` хранится со знаком: списание отрицательное, поступление положительное. Это делает расчёт баланса счёта простым суммированием:

```sql
opening_balance + SUM(amount_account)
```

Для отчётов по расходам используется `SUM(ABS(amount_account)) WHERE kind = 'expense'`.

### 7.2. Представление перевода

Перевод между счетами — две транзакции с общим `transfer_group_id`:

| Нога      | Счёт     | `amount_account` | `kind`     |
| --------- | -------- | ---------------- | ---------- |
| Исходящая | USD-счёт | −100.00          | `transfer` |
| Входящая  | EUR-счёт | +92.40           | `transfer` |

Кросс-курс выводится из двух сумм. Переводы исключаются из отчётов по доходам и расходам: это перемещение, а не изменение состояния капитала.

## 8. Функциональные требования

### 8.1. Регистрация и вход

- Регистрация: email, имя, пароль — и ничего больше. Подтверждение email письмом.
- **Первичная настройка (онбординг)** — модальное окно поверх главной страницы после первого входа, а не поля на форме регистрации и не отдельный экран: базовая валюта и таймзона требуют решения от человека, который ещё не открывал приложение. Приложение под окном видно, и два вопроса читаются как «осталось настроить», а не как продолжение регистрации. Предзаполняются по `Intl.DateTimeFormat().resolvedOptions()`.
- Окно нельзя закрыть ни Esc, ни кликом по фону: без базовой валюты и таймзоны приложению нечем считать. Недоступность остального интерфейса обеспечивает сам `<dialog>.showModal()` — для мыши, клавиатуры и скринридера одновременно, без ручной ловушки фокуса.
- Таймзона выбирается из списка, сгруппированного по регионам и отсортированного по смещению, а не вводится текстом: точный IANA-идентификатор (`Europe/Kyiv`, а до 2022 года `Europe/Kiev`) человек не угадает, и текстовое поле означало бы либо «оставил как есть», либо ошибку.
- До прохождения онбординга `base_currency` и `timezone` пусты, а приложение закрыто модальным окном на любой своей странице. Признак пройденной настройки — отдельная колонка `onboarded_at`, а не заполненность этих полей: онбординг прирастает шагами (первый счёт — фаза 1), которым не соответствует ни одна колонка в `users`.
- Онбординг проходится один раз; повторный вызов эндпоинта отклоняется. Менять эти настройки потом — через `PATCH /settings`.
- Автоматически создаётся набор категорий по умолчанию и один счёт.
- Сброс пароля по email-токену (одноразовый, 1 час). Смена пароля отзывает все сессии кроме текущей.

### 8.2. Счета

- CRUD. Валюта задаётся при создании и далее неизменяема (иначе вся история операций становится некорректной).
- Типы: наличные, банковский счёт, карта, вклад, криптокошелёк.
- Начальный остаток (`opening_balance`) на дату открытия.
- Архивация вместо удаления для счетов с историей операций.
- Сортировка пользователем вручную.

### 8.3. Транзакции

- Создание дохода, расхода, перевода.
- Сумма вводится **в любой валюте**, не обязательно в валюте счёта. При несовпадении подставляется актуальный курс, который пользователь может переопределить вручную — например, чтобы указать фактический курс обмена с учётом комиссии.
- Поля: сумма, валюта, счёт, категория, дата, примечание, теги.
- Список с фильтрами: период, счёт, категория, тип, диапазон сумм, поиск по примечанию. Курсорная пагинация.
- Редактирование и удаление (soft delete).
- Массовые операции: смена категории, удаление.
- **Идемпотентность**: `POST /transactions` принимает заголовок `Idempotency-Key`. Повторная отправка с тем же ключом возвращает существующую запись, а не создаёт дубль. Защищает от двойного нажатия и повторов на нестабильной мобильной сети.

### 8.4. Категории

- Иерархия в два уровня (группа → категория).
- Раздельные деревья для доходов и расходов.
- Иконка и цвет.
- Набор по умолчанию заводится при первичной настройке (§8.1), а не при регистрации: там уже известен язык запроса, и названия создаются на нём. Дальше это пользовательские данные — смена языка интерфейса их не переименовывает.
- При удалении категории с операциями — перенос операций в другую категорию или в «Без категории».

### 8.5. Мультивалютность и курсы

- Справочник валют: основные фиатные + основные криптовалюты.
- Курсы загружаются ежедневно фоновой задачей и складываются в `exchange_rates`.
  - Фиат: ECB (бесплатно, без ключа) или exchangerate.host.
  - Криптовалюты: CoinGecko.
- Обязателен фолбэк на последний известный курс при недоступности источника или исчерпании лимита запросов. Отсутствие свежего курса не должно блокировать ввод операции.
- Исторические курсы не перезаписываются.

### 8.6. Сводный баланс

- Баланс каждого счёта в его валюте.
- Сводный баланс по всем счетам в базовой валюте, конвертация по актуальному курсу.
- Переключение базовой валюты отображения без изменения данных.
- Разбивка: сколько в каждой валюте, доля каждого счёта.
- График net worth во времени строится по `net_worth_snapshots` (ежедневная фоновая задача), а не пересчётом всей истории при каждом запросе.

### 8.7. Регулярные операции

- CRUD правил: название, счёт, категория, сумма, валюта, периодичность (ежедневно / еженедельно / ежемесячно / ежегодно, каждые N периодов), дата начала и окончания.
- **Политика короткого месяца** задаётся явно: правило на 31-е число в феврале либо прижимается к последнему дню месяца, либо пропускается (`month_end_policy`).
- Режим `auto_post`: транзакция создаётся автоматически либо попадает в очередь на подтверждение пользователем.
- Пауза правила без удаления.
- Просмотр предстоящих списаний на N дней вперёд.
- При изменении правила ранее созданные транзакции не меняются.

**Механизм генерации** — двухуровневый:

1. Ежедневная задача pg-boss создаёт экземпляры, у которых наступила дата.
2. **Догоняющая генерация** при входе пользователя: досоздаются все пропущенные экземпляры до текущей даты.

Второй уровень обязателен: если сервер был недоступен, задача по расписанию не отработает, и списания будут потеряны безвозвратно. Воркер — лишь триггер, а не источник истины.

Даты вычисляются в таймзоне пользователя: иначе «1-е число» наступит для части пользователей 28-го в 23:00.

### 8.8. Напоминания и сверка остатков

- Настройка напоминания: день месяца (или «последний день месяца»), время, каналы доставки.
- Каналы: внутреннее уведомление (первая версия), email. Web Push — вне скоупа v1.
- По напоминанию пользователь вводит фактический остаток по каждому счёту.
- Приложение сохраняет введённый и расчётный остаток и показывает **расхождение**. Это основной инструмент контроля качества учёта: расхождение означает незафиксированную операцию.
- По расхождению можно создать корректирующую транзакцию одним действием.
- История сверок по счёту.

### 8.9. Отчёты

- Расходы по категориям за период (круговая и столбчатая диаграммы).
- Динамика по месяцам, сравнение месяц к месяцу.
- Кэшфлоу: доходы минус расходы по периодам.
- Net worth во времени.
- Структура по валютам.
- Топ категорий и крупнейшие операции за период.
- Экспорт отчёта в CSV.

### 8.10. Бюджеты

- Лимит на категорию на календарный месяц.
- Прогресс расходования, предупреждение при приближении к лимиту.
- Перенос неиспользованного остатка на следующий месяц (опционально, настройкой).

### 8.11. Импорт и экспорт

- Импорт CSV с сопоставлением колонок и предпросмотром.
- Дедупликация при повторном импорте по хешу строки.
- Полный экспорт данных пользователя в CSV и JSON.

## 10. Нефункциональные требования

### 10.1. Безопасность

- Все требования §6.5.
- Заголовки безопасности: `@fastify/helmet`, строгий CSP.
- CORS — только для домена фронтенда, с `credentials`.
- Параметризованные запросы везде (обеспечивается Drizzle).
- Секреты не запекаются в Docker-образ, передаются через переменные окружения в рантайме.
- Логи не содержат токенов, паролей и значений cookie.
- Изоляция данных пользователей покрывается интеграционными тестами: обращение к чужому ресурсу возвращает 404, а не 403 — чтобы не раскрывать факт его существования.

### 10.2. Надёжность данных

- **Бэкапы обязательны.** `pg_dump` по расписанию с выгрузкой в S3-совместимое хранилище, срок хранения 30 дней.
- Проверка восстановимости дампа — регулярная. Непроверенный бэкап бэкапом не является.
- Миграции — отдельным шагом деплоя, не в стартовом хендлере приложения (иначе при нескольких репликах возникнет гонка).

### 10.3. Производительность

- Индексы: `transactions (user_id, occurred_on DESC)`, `transactions (account_id, occurred_on)`, `sessions (refresh_token_hash)`, `exchange_rates (base, quote, date DESC)`.
- Балансы в первой версии считаются на лету; при росте объёма данных — кэш в отдельной таблице с инвалидацией.
- Курсорная пагинация для списка транзакций.

### 10.4. Тестирование

- Unit: денежная арифметика, конвертация, вычисление дат регулярных правил — с акцентом на граничные случаи: 29–31 число, февраль, переход года.
- Integration: эндпоинты на реальном Postgres (testcontainers), проверка изоляции данных и идемпотентности.
- E2E: регистрация → вход → создание счёта → операция → отзыв сессии.

### 10.5. Локализация

- Интерфейс: русский и английский, с самого начала через словари (не хардкод строк).
- Словари — по одному JSON-файлу на язык в `packages/shared/src/i18n/locales`. Там же, а не во фронтенде, потому что сообщения валидации рождаются в zod-схемах и показываются обеими сторонами: формой до отправки и API после.
- Сообщения валидации и ошибок внутри приложения ходят **ключами**, а не готовым текстом. Текст появляется в одном месте на каждой стороне: на сервере — в обработчике ошибок по `Accept-Language`, на клиенте — в компоненте.
- Числа в тексте подсказок передаются параметром из той же константы, которую проверяет схема (`LIMITS`): «Минимум 8 символов» не может разойтись с проверкой, требующей восемь.
- Фронтенд — i18next: нужны формы множественного числа (в русском one/few/many), смена языка без перезагрузки и запоминание выбора. Язык определяется из `localStorage`, затем из браузера.
- Полнота словарей проверяется тестом: набор ключей во всех языках совпадает (кроме форм множественного числа, которых в разных языках разное количество), пустых строк нет, у плейсхолдеров есть пара в каждом языке.
- Форматирование сумм и дат — `Intl`, по локали и валюте.
- Вне охвата: письма (верификация email, сброс пароля) отправляются на русском — язык получателя в момент отправки неизвестен, его нужно хранить в `users`. Фаза 6, вместе с провайдером рассылки.

## 14. Отношение к существующему прототипу

В репозитории находится прототип на CRA + Express + MySQL с JWT-аутентификацией без сессий.

**Переносится:**

- `frontend/src/scss` — миксины, `adaptiveValue`, `null.scss`, стили форм входа. Единственная часть прототипа, содержащая завершённую работу.
- Разметка форм входа и регистрации, компонент `PasswordInput`.

**Не переносится** (заменяется в силу смены стека и модели аутентификации):

- Весь `backend/` — переход с MySQL на Postgres, с callback-API `mysql2` на Drizzle, с JWT-без-сессий на access + refresh с ротацией.
- Сборка CRA → Vite, JavaScript → TypeScript.

Реструктуризация выполняется в текущем git-репозитории с сохранением истории, в отдельной ветке.
